# zM1 UART RX type 0x0F / 0x18 定点分析

参考文件：`reference/zM1@MK3080B@moc.ota.bin`，APP payload 位于 OTA `0x75008`，链接基址 `0x08088008`。只检查 RX parser `0x0808be88` 的 `0x0F`、`0x18` 分支及其直接调用链，以及主循环中一处 type `0x01` 发送入口。地址可用 ARM GCC 5.4.1 的 `arm-none-eabi-objdump -D -b binary -m arm -M force-thumb --adjust-vma=0x08088008` 复核。

## 实机输入

用户在 UART1、115200 8N1 收到 20 字节帧，首尾是 `23` / `21`。type `0x0F` 实例为 `23 0F 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 21`，随后出现 `[2]=01` 的同型帧。方向是 **ATSAMD20 → EMW3080**。type `0x0C` 的 `[2..8]` 已与 M1 实时日期时间逐项吻合；本报告不扩展分析其业务调用链。

## type 0x0F：亮度/显示开关回报

- 分发：`0x0808bf8a` 比较类型 `0x0f`，跳到分支 `0x0808c084`；分支在 `0x0808c0b0` 前返回，完整分支范围 `0x0808c084–0x0808c0b0`。
- `0x0808c084` 申请 48 字节临时缓冲；失败则跳过。
- `0x0808c08e` **只读取 `frame[2]`**。若其为 `0`，传给格式化函数的亮度值为 `0`；若非零，`0x0808c092–0x0808c094` 读取 RAM `0x10030001` 的已保存亮度档位。其余帧字节不参与该分支判断。
- `0x0808c096–0x0808c09c` 用位于 `0x080a07f5` 的确切格式串 `{"mac":"%s","brightness":%d}` 构造 JSON；MAC 字符串取自 `0x10030218`。`0x0808c0a4` 以 `r0=0`、`r1=JSON` 调用 `0x0808d108`，然后释放临时缓冲。
- `0x0808d2de–0x0808d2f2` 在该通用 JSON 函数中取 `brightness` 数字，并调用 `0x0808be08`。后者在 `0x0808be0e–0x0808be30` 更新 RAM `0x10030000`（亮/灭标志）及 `0x10030001`（非零亮度档位），在 `0x0808be34` 调用 PWM/亮度处理函数 `0x0808c49c`，再经 `0x0808bcbc` 入 UART TX 队列。队列消费者于 `0x0808c2ee` 调用 MOC UART 发送 veneer。
- `0x0808be38–0x0808be50` 构造 12 字节 TX：`23 02 XX YY 00 00 00 00 00 00 00 21`。`XX=RAM 0x10030001 中保留的亮度档位×25`，`YY=0` 表示关、`1` 表示开。关闭时 `0x0808be28` **只清亮/灭标志，不清亮度档位**，所以 `[2]=00` 在保留档位 4 时发送 `23 02 64 00 00 00 00 00 00 00 00 21`；`[2]=01` 恢复档位 4 时发送 `23 02 64 01 00 00 00 00 00 00 00 21`。档位来自全局 RAM，无法仅由 RX 帧确定，因此两个分支都没有跨设备唯一固定的 TX HEX。

**结论**：`frame[2]` 是亮度关闭/恢复请求或状态输入，具体是否由某颗实体按键产生仍未由代码调用链证明。此分支没有直接调用 Wi-Fi API；生成的 JSON 只有 `mac` 和 `brightness`，没有 Wi-Fi 状态字段。它会间接触发 UART TX，但证据指向显示亮度，**不是 Wi-Fi 图标 ON/OFF 命令**。OpenM1 v0.5.0 复刻已确认的亮度回复并抑制短时回环，亮度控制本身尚需实机验证。

## type 0x18：确认帧与重置路径

- 分发：`0x0808bf8e` 比较 `0x18`，跳到 `0x0808c0b4`；分支到 `0x0808c0f0`，失败/普通返回走 `0x0808c0f4`。该分支**不读取 `frame[2..18]`**。
- `0x0808c0b4–0x0808c0ba` 将 RAM `0x100305b0` 的计数加 1；`0x0808c0bc` 每次调用 `0x0808be64`。此函数把 ROM `0x080a06e0` 的固定 12 字节 `23 16 00 10 14 00 03 10 F1 FF FF 21` 放入同一 UART TX 队列；最终由 `0x0808c2ee` 发送。
- `0x0808c0c0–0x0808c0c6` 仅在**有符号计数大于 1**时继续：调用 `0x08088080` 恢复配置默认字段、清零某配置标志、调用 `0x080921cc` / `0x08092288` 的配置路径、等待约 50 ms，最后 `0x0808c0f0` 尾调用 `0x080919a8`。按照固定 SDK `moc_api.h` 的接口表布局，`0x080919a8` 通过偏移 `0x28c` 跳转到 `MicoSystemReboot`（首字段 `library_version` 占 4 字节）。

**结论**：type `0x18` 至少是有确认帧的重置流程；重复触发后会恢复部分配置并重启。其外部触发来源（例如哪颗实体按键）尚未证实。它不是传感器数据帧，也没有直接发送 type `0x01` 请求。

## type 0x01 请求入口

`0x0F` 的固定 JSON 只触发亮度路径；`0x18` 只发送上述 type `0x16` 确认并可能重置。两者均未发现 type `0x01` 请求。

另有**独立的主循环入口**：`0x08088616` 调用 `0x0808bde4`。后者从 `0x080a06c8` 复制 12 字节 `23 01 00 00 00 00 00 00 00 00 00 21` 并入同一 UART TX 队列；主循环在 `0x0808861a` 后延迟 100 ms 并再次循环。`0x08088604–0x08088620` 的回跳目标在该调用之前，说明该请求在进入此主循环后重复执行；本段没有读取 Wi-Fi 状态或控制图标。用户后续已在真实硬件确认单次请求产生 type `0x01` 响应，数值与实体屏幕吻合。OpenM1 v0.5.0 改为每 2000 ms 发送一次。

Android 客户端 [m1_fragment.xml](https://gitee.com/a2633063/SmartControl_Android_MQTT/blob/e5365b8a11cffa21fef0894f2db67931dffbabf4/app/src/main/res/layout/m1_fragment.xml) 的亮度 SeekBar `android:max="4"`；[M1Fragment.java](https://gitee.com/a2633063/SmartControl_Android_MQTT/blob/e5365b8a11cffa21fef0894f2db67931dffbabf4/app/src/main/java/com/zyc/zcontrol/deviceItem/m1/M1Fragment.java) 在松开 SeekBar 时发送亮度值。这与 APP `0x0808be08–0x0808be50` 中 0–4 档、档位乘 25 的构造逻辑一致。原称“UART init command”的 `23 02 64 01 ... 21` 同时是亮度 4、屏幕开启帧，不能再视为无业务含义的初始化帧。
